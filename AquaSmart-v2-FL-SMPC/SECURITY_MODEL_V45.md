# AquaSmart V4.5 — Research transport security and trust model

## Scope

- **Protocol:** V4.4 signed ephemeral X25519 announcements, Ed25519
  authentication, HKDF-SHA256 / ChaCha20 pairwise masks, finite-field
  fixed-point aggregation and signed pre-upload dropout correction.
- **Transport:** TCP loopback `127.0.0.1` and **mutual TLS 1.3** with an
  ephemeral test certificate authority generated by the benchmark parent.
  A different client certificate is generated per pond and bound to the
  client ID via the verified certificate CN. The server certificate includes
  `localhost` and `127.0.0.1` SANs, and clients verify its hostname.
- **Processes:** one spawned network-server process, one spawned client
  process for each participant. Each client creates its own protocol-private
  Ed25519 signing and ephemeral X25519 agreement keys **inside its child
  process**, not in the server. The benchmark parent generates TLS dev keys
  and sees plaintext updates; separate **processes do not imply privacy from
  the test harness**.
- **Trust model:** Honest clients, noncolluding **honest-but-curious server**,
  authentic server-provisioned mTLS identities. The server must truthfully
  broadcast every valid received masked upload before recovery.

## Detailed round

1. Benchmark parent generates one-off dev CA and TLS certificates in a
   temporary directory and starts the server and 11 clients using OS spawn.
2. Clients mutually authenticate TLS, announce an ephemeral signed X25519 key
   and an Ed25519 verification key bound to their TLS client certificate.
3. Server returns all authenticated announcements and public verification
   keys to each client over TLS. Clients independently build the same
   transcript hash and compute pairwise masks.
4. All clients locally **in the benchmark** receive clear weighted model
   updates passed by the parent process. Selected dropouts close their TLS
   sessions after announcement but before upload. Others send signed masked
   updates. The server waits until all clients either uploaded or disconnected.
5. Server returns the exact list of signed uploaded updates. Survivors verify
   those signatures and send signed correction vectors **only for clients
   absent before upload**; honest noncolluding behavior is assumed.
6. Server verifies proof count/signatures and returns aggregate; if fewer
   than two clients upload, or a *post-upload* dropout occurs, reject round.
7. Each receiver checks the returned aggregate equals the server output;
   experiment compares it against plaintext FedAvg with the same survivors.

## Unsupported threats and critical caveats

- No threshold secret sharing, no malicious-server resistance, no collusion
  defense, no robust byzantine aggregation and no differential privacy.
- In a malicious coordinator model, falsely claiming an uploaded client
  dropped may cause survivors to reveal unintended mask corrections.
  **Not secure against such a coordinator**. Honest-but-curious assumption
  is essential, not a minor deployment detail.
- Server distributes clients' ephemeral Ed25519 public keys based on mTLS
  authentication **within a single session**. In real deployment, enrollment
  needs an out-of-band identity registry / pinned public keys.
- All application messages are JSON framed over TLS. `tls_application_frame_bytes`
  measures **plaintext JSON plus 4-byte length prefix** observed at TLS
  APIs (both directions per client). It excludes TLS handshake records,
  record tags, retransmissions and headers and is not a packet-level WAN
  bandwidth estimate.
- Keys/certificates are temporary, generated centrally in benchmark parent,
  and removed after the round. They are **not production PKI**, nor securely
  provisioned for cross-host operation.
- All local training runs in the parent benchmark before the client child
  processes are started; the benchmark parent is a trusted testing harness,
  not a private federated client. End-to-end client-private FL remains future work.
- A fallback path for failures after a signed upload would require a
  formally specified, independently reviewed protocol with secret sharing
  and explicit corruption and availability assumptions.
- The feeding label is simulated from a deterministic heuristic plus noise.
  VALIDATION-only benchmark shares time windows with previous exploration;
  no independent final TEST was measured.

## Suggested next research validation

1. Client-local training on separately provisioned machines; per-client
   secure data ingestion and independent identity credentials.
2. Controlled packet capture for full TLS wire-byte and latency accounting,
   repeated measurements under network conditions and hardware constraints.
3. Formal dropout-threshold design with peer-reviewed secure aggregation;
   verify against malicious coordinator / collusion assumptions in tests.
4. Independent out-of-time test partitions and measured feeding targets where
   possible, with independent experiments across ponds and periods.
